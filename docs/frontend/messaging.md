## Messaging Identity

- Directness: direct and specific; explain mechanisms instead of using
  marketing slogans.
- Formality: friendly technical documentation, not corporate whitepaper copy.
- Technical depth: high enough for developers and crypto-native readers; avoid
  beginner-only crypto education.
- Claim confidence: cautious on performance and risk; confident on explaining
  architecture and repository workflows.
- Emotional intensity: warm, curious, and practical.
- Humor: light mascot warmth is allowed; jokes must not weaken risk clarity or
  technical trust.
- Relationship to the user: a lab notebook that helps capable readers orient
  quickly.
- Natural phrases: research desk, strategy lifecycle, exact backtest,
  execution boundary, curated guide, closed-candle decision path.
- Foreign phrases: guaranteed returns, effortless profits, AI trading magic,
  institutional-grade alpha, fully automated money machine.
- Owner preference signals: public English docs; huge curated portal; lo-fi
  cute visual tone; for developers and crypto-native readers; no private
  pages; neutral public live architecture.
- Private owner language not suitable for public copy: raw chat shorthand,
  private live-money details, account state, and production runtime values.
- Evidence: owner onboarding answers on 2026-09-01 and repository README.

## Messaging Contract

- Page or screen: docs home / system map.
- Why it exists: orient readers to the whole project before they choose a
  guide, subsystem, or glossary concept.
- Audience: developers and crypto-native readers.
- Starting user state: interested but unsure how the repository pieces fit.
- Intended leaving state: understands the system shape and has a clear next
  route.
- Main idea: `crypt` is a Python research desk for crypto strategies, organized
  around data, strategy logic, backtesting, results, and neutral execution
  architecture.
- First messages: what the project is, who it is for, and the clickable system
  map.
- Later messages: subsystem details, guide paths, version scope, and risk
  boundaries.
- Objections to answer: whether the docs are curated, whether private live
  details are exposed, whether the project promises trading returns, and where
  code evidence lives.
- Required proof: visible map, source-linked sections, search results, and
  guide pages with command/output/explanation steps.
- Natural action: click a map node, search, choose Developer or Crypto Trader
  journey, or open a guide.
- Generic-copy risks: broad "unlock crypto alpha" statements and ornamental
  mascot text that does not clarify the system.

## Message Trajectory

- Starting state: reader sees a large Python trading repository and needs a
  mental model.
- Problem or tension: strategy research, exact backtests, and execution
  boundaries are hard to understand from files alone.
- Product explanation: the portal curates the project into a system map,
  guides, references, glossary, and versioned docs.
- Mechanism: every major subsystem gets a page, diagrams explain flow, guides
  show commands with expected output and explanation, and search indexes
  curated concepts.
- Proof: source links, architecture-node coverage, route inventory, and
  version-scoped examples.
- Objection handling: separate public architecture from private live operations
  and put trading risk in a dedicated Risk & Limits section.
- Action: start with the map, use search, or follow a role journey.
