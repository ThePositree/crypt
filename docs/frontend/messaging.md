## Messaging Identity

- Directness: high; state mechanisms and boundaries plainly.
- Formality: professional and concise.
- Technical depth: moderate; name OKX, backtests, runtime config, fills, and
  regression evidence without explaining every internal detail.
- Claim confidence: conservative; avoid performance promises and soften any
  illustrative chart language.
- Emotional intensity: low.
- Humor: none.
- Relationship to the user: operator/researcher using an internal workbench.
- Natural phrases: research workbench, live execution module, runtime truth,
  exact backtests, evidence, dry-run.
- Foreign phrases: none.
- Owner preference signals: Russian owner chat; English code/docs.
- Private owner language not suitable for public copy: chat shorthand such as
  "делаем сайт" is not used in public UI.
- Evidence: `README.md`, `docs/state/current.yml`, and local AGENTS rules.

## Messaging Contract

- Page or screen: site homepage.
- Why it exists: provide a first read-only web surface for repository context.
- Audience: owner, agents, or technical reviewers.
- Starting user state: has repository access but needs orientation.
- Intended leaving state: knows the project shape and canonical docs.
- Main idea: `crypt` joins research evidence and live execution while keeping
  runtime money truth outside the static site.
- First messages: automated crypto perpetual strategy workbench; research,
  validate, and operate the owner-selected live strategy.
- Later messages: discovery, exact backtests, benchmark reporting, runtime
  config, OKX truth, and reconciliation evidence.
- Objections to answer: live-control risk, unsupported profit claims, and where
  to inspect evidence.
- Required proof: local links to README and canonical docs.
- Natural action: open README, benchmark, evidence docs, or runbook.
- Generic-copy risks: AI trading buzzwords, guaranteed returns, and dashboards
  that appear to be live account data.

## Message Trajectory

- Starting state: visitor lands on the repository site.
- Problem or tension: strategy research and live execution can be confused if
  evidence and money boundaries are not explicit.
- Product explanation: `crypt` is a research workbench plus live OKX execution
  module.
- Mechanism: closed-candle decisions, exact backtests, archived candidates,
  runtime config, exchange sync, and reconciliation.
- Proof: links to canonical markdown sources.
- Objection handling: site is read-only; OKX/runtime remain truth.
- Action: inspect README, benchmark, evidence docs, or dry-run command.

## Objection Map

- Objection: the site may control live money.
- Where it arises: execution section and console-like hero panel.
- Response: label the panel read-only and state that runtime config and OKX
  remain truth.
- Placement: hero status chip and live execution section.
- Evidence: static implementation.

## Microcopy Rules

- Buttons and links: use concrete destinations, not vague "learn more" labels.
- Navigation labels: name durable product areas.
- Forms: not in scope.
- Loading states: not in scope for static site.
- Empty states: not in scope.
- Error states: not in scope.
- Success states: not in scope.
- Confirmations: not in scope.
- Tooltips and badges: badges should clarify trust boundary or status.
